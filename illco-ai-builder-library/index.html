Chapter 1

A Prototype Is a Question, Not a Product

The first version of an AI product has one job: prove that something important is possible. It does not have to prove that the system is scalable, the interface is finished, every integration is reliable, or every edge case has been discovered.

A prototype answers a question. Can an AI generate the required output? Can the browser render the world? Can a model call the tool? Can the application retrieve the right document? Can a character fly through a large environment? Can a workflow turn an input into a useful finished artifact?

Production asks something much harder: Can it do it again, correctly, under real conditions, when nobody is standing over the system fixing whatever breaks?

The Seduction of the Working Demo

AI dramatically compresses the distance between an idea and something that appears to work. It can generate the interface, populate it with realistic content, create assets, write supporting code, produce a test result, describe the architecture, and confidently explain that the requested feature has been implemented.

The closer an unfinished system looks to a finished system, the easier it becomes to mistake appearance for capability.

A game can show a city without having the required city data correctly integrated. A 3D pipeline can produce an attractive render without proving that the render came from the exported GLB. A deployment can succeed while the application still enters an unwanted fallback path. A tool integration can work once without appropriate retry, authentication, observability, or recovery behavior.

Define the Claim Before Building

A vague requirement allows almost any plausible result to masquerade as success. A production requirement must describe observable behavior. This leads to a basic pattern:

Requirement → Claim → Evidence → Acceptance

The requirement describes what is wanted. The claim describes what the implementation supposedly accomplishes. The evidence demonstrates whether the claim is true. The acceptance rule determines whether that evidence is sufficient.

The Las Vegas Problem

Our Las Vegas game work amplified every architectural mistake. The world specification became concrete: a primary projected coordinate system, explicit geographic bounds, and a 35 × 35 grid covering roughly 35 × 35 kilometers. That means 1,225 one-kilometer sections.

“Build Las Vegas” is a creative instruction. A 35 × 35 kilometer world with coordinate systems, tile dimensions, terrain sampling, manifests, shared boundaries and known geographic anchors is an engineering specification.

Why Tiling Changes Everything

A monolithic world asset increases download time, parsing time, memory pressure, GPU usage, collision complexity and recovery cost. Tiling changes the unit of responsibility:

Player position
      ↓
World coordinate
      ↓
Tile coordinate
      ↓
Required tile set
   ↙   ↓   ↘
terrain roads buildings
      ↓
Runtime scene

The runtime no longer needs to understand “Las Vegas” as one indivisible object. It needs to understand the player’s current neighborhood.

The Manifest Becomes the Truth

Once assets are distributed, the project needs a reliable source of truth. The manifest establishes the contract between the asset pipeline and runtime. The runtime should not guess what exists. Humans should not have to remember where everything is. Agents should not independently invent paths.

This is why production AI engineering is often less about making the model smarter and more about reducing the number of decisions the model is allowed to improvise.

The Evidence Ladder

Completion evidence grows stronger as we move from assertion, to artifact existence, to structural validation, functional validation, integrated validation, user-visible proof and finally recovery validation.

The strongest practical rule is simple: proof must come from the artifact being accepted. If testing a GLB, reopen and render the exported GLB. If testing a deployment, test the deployed URL. If testing an archive, reconstruct and verify the archive. Test what the user will actually receive.

Failure Is Data

A failed attempt can reveal an unstated requirement, invalid assumption, architectural bottleneck, ambiguous contract, missing validation step, unsupported environment, resource limit or integration boundary. The right question is not merely “How do we retry?” but “What did this failure teach us that should permanently change the system?”

DEFINE → BUILD → INSPECT → TEST → BREAK
   → RECORD → HARDEN → DEPLOY → OBSERVE → REPEAT

Chapter Takeaway

A prototype proves that an idea can work. Production proves that the system does work under defined conditions, can demonstrate that it worked, and can respond predictably when it does not. Move from “It looks finished” to “Here is the evidence.”

Chapter 2

Turn the Idea Into a System Before You Turn It Into Code

The fastest way to waste the speed AI gives you is to start building before deciding what you are actually building. Generative AI can produce interfaces, schemas, API routes, buttons, game code, authentication, artwork and deployment configuration in minutes. Code generation is not the same thing as system design.

The solution is not months of specification. It is a minimum viable architecture before the minimum viable product.

The Prompt Is Not the Specification

“Build a creator platform where customers can pay to call creators” hides dozens of system decisions: identity, creator authorization, wallet semantics, billing start conditions, queue behavior, low-balance handling, disconnects, authoritative timers, refunds, moderation and accounting.

Our creator-platform work became easier to reason about when the concept was decomposed into responsibilities such as identity, payments, wallet ledger, call sessions, queues, billing, moderation and administration.

Start With Invariants

Before choosing frameworks, define what must always remain true. A prepaid calling system might require: balances never go negative, waiting is not billable, only active sessions create usage charges, every balance change is traceable, the server is authoritative for billable duration, and terminated sessions cannot keep accruing charges.

These rules survive technology choices. They can also be attacked with AI: ask a model to find contradictions, identify race conditions, and generate tests capable of proving each invariant.

Convert Features Into State Machines

CREATED → WAITING → CONNECTING → ACTIVE
                              ↘
                          ENDING / FAILED
                              ↓
                            ENDED

State machines expose the production questions: what if payment succeeds but the call never becomes active? What if the browser disappears? What if termination events race? What happens on reconnect?

The Ledger Pattern

A displayed balance is not sufficient accounting. A ledger records why the balance changed. The current balance can be materialized for speed, but its history must remain traceable. Currency should generally be represented in its smallest unit, such as cents, rather than floating-point dollars.

Separate Authority From Presentation

The browser can display the timer; the server should determine billable time. The client can display player coordinates; the world system should determine authoritative placement. The interface can show an AI artifact; the validation pipeline should determine whether it satisfies the contract.

PRESENTATION STATE = what the user sees
AUTHORITATIVE STATE = what the system considers true

Decompose by Responsibility, Not by Screen

A project organized only around pages tends to duplicate logic. Stronger boundaries center on responsibilities: identity, wallet, payments, sessions, billing, moderation, notifications and analytics. Shared contracts allow multiple interfaces to use the same underlying system.

Build the File Tree Before the Files

apps/
  web/
  creator-dashboard/
  admin/
  api/

packages/
  auth/
  billing/
  database/
  schemas/

ai/
  prompts/
  agents/
  evaluations/

integrations/
mcp/
tests/
infra/
docs/

The exact tree varies, but the principle does not. Decide where shared logic, schemas, prompts, integrations, tests, operational documents and deployment definitions belong before agents generate large amounts of code.

Architecture Decision Records

AI projects move quickly enough that even solo builders forget why decisions were made. A short Architecture Decision Record preserves context such as why a large world must remain tile-addressable rather than being merged back into one huge asset.

Design Failure Before Success

Production specifications must describe failure behavior: retries, idempotency, checkpoints, backoff, transactional boundaries and compensating actions. Retry safety is architecture. A payment, deployment or publishing operation should not duplicate itself merely because acknowledgement was lost.

The Minimum Viable Architecture Document

Before substantial implementation, define the product objective, actors, invariants, subsystems, authoritative data, state machines, contracts, failure behavior, security boundaries, observability, acceptance evidence and explicit non-goals.

AI changes the economics of writing code. It does not repeal the economics of complexity. Cheap code actually makes architecture more important because complexity can accumulate faster than a human notices it.

Chapter Takeaway

Do not begin a serious AI product by asking what code to generate. Ask what must remain true while the system is running. Define actors, states, authorities, contracts, failure behavior, evidence and non-goals. The goal is not to prevent AI from making decisions; it is to prevent important architectural decisions from being made accidentally.

Chapter 3

Build the Smallest Vertical Slice That Can Tell You the Truth

A minimum viable product is often misunderstood as a smaller version of the final product. The most useful early build is the one that crosses enough of the real system to expose whether the architecture actually works.

For a large browser game, that may mean one geographically correct world section, one controllable character, one vehicle, one streamed neighboring section and one representative interaction. That is a vertical slice.

Horizontal Progress Can Be Misleading

A team can generate hundreds of models, animations, screens, tools and terrain tiles without proving that one player can enter the world, move through a correctly placed section and cross into another without failure. The project has accumulated assets, but it has not yet proved the game.

Launch → WebGL2 → Spawn → Correct tile
→ Terrain → Roads → Buildings → Movement
→ Collision → Boundary crossing → Stream next tile
→ Unload distant assets

The First Slice Should Be Representative, Not Easy

Do not pick an empty kilometer merely because it yields a fast green result. Include representative difficulty: irregular roads, multiple buildings, terrain variation, sidewalks, curbs, a large asset, collisions, an adjacent boundary and enough visual complexity to expose performance problems.

The Thin-Slice Formula

one user + one primary goal + one complete path + one difficult dependency + one failure condition + one measurable outcome

For image-to-3D, that could be upload → reconstruction → texture → export → reopen → render, with the exported GLB required to reopen successfully and the proof image required to come from that same file.

Do Not Mock the Thing You Most Need to Learn

Mocks are valuable only when they replace dependencies that are not under investigation. If GLB performance is the biggest uncertainty, use representative GLBs. If geographic alignment is the biggest uncertainty, use actual coordinate transformations. If payment reliability is the risk, use a real sandbox flow. Never mock the primary risk.

Anchor Tests

Large systems benefit from facts whose expected outcomes are known independently of the generated system. A known landmark can verify geographic transformations. A fixed transaction sequence can verify accounting. A known source passage can verify retrieval. Anchors turn “looks about right” into numerical debugging.

Golden Paths and Poison Paths

Test the expected journey, then deliberately introduce failure. What happens when a neighboring tile is missing? When a tool times out? When an optional asset cannot load? The question mark in the failure path is where architecture lives.

Build the Instrument Panel Early

The first slice should expose what loaded, what failed, how long each stage took, how much memory is used, which model or tool ran, what asset version loaded, and what state transition occurred. Otherwise debugging becomes archaeology.

Performance Budgets Must Exist Before Optimization

“Make it fast” is not a requirement. Frame time, startup time, memory, GPU memory, draw calls, triangle counts, texture sizes, network transfer, simulation counts and loading latency need explicit budgets appropriate to the target hardware.

30 FPS → about 33.3 ms per frame
60 FPS → about 16.7 ms per frame

That budget must cover input, gameplay logic, physics, animation, AI, streaming, rendering and browser overhead.

Fidelity Should Follow Player Attention

Not every object deserves maximum fidelity. Distant structures can use simplified geometry, compressed textures and minimal collision. Nearby interactive assets can receive more detail. AI-generated surface imagery can provide visual density while geometry supplies silhouette, collision and major depth.

Theme Variants Should Share Structure

A normal, heaven-themed and hell-themed city should share authoritative terrain, roads, curbs, sidewalks, driveways, footprints and base geometry wherever possible. Materials, lighting, effects, decals and selective landmark geometry can vary by theme. Fix geographic errors once, not three times.

Stop Expanding When the Slice Fails

FREEZE SCOPE
   ↓
IDENTIFY FAILURE
   ↓
REDUCE VARIABLES
   ↓
FIX ROOT CAUSE
   ↓
ADD REGRESSION TEST
   ↓
RERUN SLICE

If the world cannot load reliably, do not add another superpower. If the wallet cannot reconcile, do not add another payment method. If retrieval cannot identify evidence, do not scale automatic publishing.

The Expansion Ladder

Scale deliberately: one tile → two adjacent tiles → a 3×3 neighborhood → a representative district → multiple districts → the full world. The same pattern applies to agents, documents, workflows and services.

Chapter Takeaway

Build one representative vertical slice that crosses the real architecture. Use the real dependencies that contain the greatest uncertainty. Establish anchors, test a golden path and a poison path, measure performance, and stop expanding when the slice fails. The first production build exists to tell you the truth as cheaply and early as possible.
